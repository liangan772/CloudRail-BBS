# 02 系统架构与后端接入

> 本文档是本项目最重要的技术文档：定义前端如何接入 Discourse 后端。
> 所有端点与设置名以**部署实例实测**及官方文档 docs.discourse.org 为准；本表已按 Discourse 2026.x 整理。

## 1. 总体架构

```
                    ┌──────────────────────────────────────────────┐
 用户浏览器 ───────► │ nginx（forum.example.com:443）                │
                    │  ├─ / 及前端路由        → Nuxt SSR（127.0.0.1:3000）│
                    │  ├─ /session /message-bus /uploads /user-api-key │
                    │  │  /raw /srv 及 *.json → Discourse（127.0.0.1:3001）│
                    │  └─ /admin 等系统路径   → 仅内网/管理员白名单    │
                    └──────────────────────────────────────────────┘
                                   │
                     ┌─────────────▼──────────────┐
                     │ Discourse 官方 Docker 容器  │
                     │  Rails(Puma) + Postgres    │
                     │  + Redis + Sidekiq         │
                     └────────────────────────────┘
```

核心原则：

1. **Discourse 是唯一数据源**，前端不做任何写库操作。
2. **同域（单域名）部署**：登录 Cookie、上传、WebSocket 全部同域，无需 CORS，这是默认形态。
3. **前端拥有全部用户可见路由**（/、/t/:id、/c/:slug、/u/:username、/search 等），Discourse 原生页面不对外；仅"系统路径"白名单反代给 Discourse。
4. 管理员通过 Discourse 自带后台（/admin，IP 白名单）治理站点。

## 2. 部署形态

### 形态 A（默认，推荐）：单域名白名单反代

nginx 配置骨架（完整版见 docs/08）：

```nginx
# 前端 SSR
location / {
    proxy_pass http://127.0.0.1:3000;
}

# Discourse 系统路径白名单（按需增删，转发到 Discourse 容器）
location ~ ^/(session|user-api-key|message-bus|uploads|srv|raw|admin|u/activate-account|u/confirm-|email|letter_avatar|user_avatar|secure-media-uploads)/ {
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $host;
    proxy_http_version 1.1;                 # WebSocket 升级（MessageBus）
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}

# JSON API 一律转发给 Discourse
location ~* \.json$ {
    proxy_pass http://127.0.0.1:3001;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

要点：

- Discourse 的 `DISCOURSE_HOSTNAME` 设置为公开域名 forum.example.com，邮件链接、上传 URL 自动正确。
- 邮件中的激活/改密链接（/u/activate-account、/u/confirm-*）与"查看话题"链接（/t/:id）分别落到代理路径或前端路由，均可用。
- 管理员后台 `/admin` 建议加 IP 白名单（`allow 内网/办公网; deny all;`）。
- 本形态下**不需要**开启 Discourse 的 CORS（`enable_cors` 保持默认关闭）。

### 形态 B（备选/演进）：双域名 + CORS + Discourse Connect

当前端需要独立域名（如未来做 APP、多端）时启用：

- 前端 `forum.example.com`，Discourse `discuss.example.com`。
- Discourse 站点设置：`enable_cors = true`、`cors_origins = https://forum.example.com`。
- 登录改用 **Discourse Connect（SSO）**：`enable_discourse_connect = true`、`discourse_connect_url`（我们的回调）、`discourse_connect_secret`。
  - 流程：前端跳转 `https://discuss.example.com/session/sso?return_path=%2F`，附带 `sso=base64(payload)` 与 `sig=HMAC-SHA256(secret, payload)`；payload 含 `nonce`、`external_id`（唯一）、`email`、`username`、`name`、`avatar_url`、`groups`、`admin`、`moderator` 等；Discourse 校验后 302 回 `discourse_connect_url?sso=...&sig=...`，我们校验签名与 nonce 后建立自己的会话。
- 或使用 **User API Key** 流（`POST /user-api-key`，用户授权后获得用户级 key，请求头 `User-Api-Key`）。
- 实时消息跨域需另行验证 MessageBus 的 CORS 配置，必要时用 nginx 反代 `/message-bus` 规避。

> 结论：MVP 一律采用形态 A；形态 B 的改造点（CORS、SSO、User API Key）已在本文档预留。

## 3. 认证与会话（形态 A）

| 场景 | 方式 |
|------|------|
| 登录 | `POST /session`，body `{login, password, second_factor_method?, otp?}`；成功后设置会话 Cookie（HttpOnly，名称以实际 `Set-Cookie` 为准） |
| 登出 | `DELETE /session` |
| 当前用户 | `GET /session/current.json`（未登录返回 403/404，前端据此切换登录态） |
| 注册 | `POST /u`，body `{name, username, email, password}` |
| CSRF | **关键**：Cookie 会话下，所有非 GET 请求必须带 `X-CSRF-Token` 头；token 从 `GET /session/csrf.json` 获取，登录后拉取并全局持有 |

前端 API 客户端必须实现：登录后自动请求 `/session/csrf.json`，在拦截器中为写操作注入 `X-CSRF-Token`。

> 服务端密钥类认证（站点级 `Api-Key` + `Api-Username` 请求头）仅在服务端脚本/测试中使用，**不进入前端代码**。

## 4. 核心 API 端点清单

约定：基础路径为 `https://forum.example.com`；除标注外均需登录；分页参数 `page`（0 起）；列表响应含 `topic_list.more_topics_url` 用于"加载更多"。

### 4.1 站点与全局

| 端点 | 用途 |
|------|------|
| `GET /site.json` | 站点配置、分类树、标签、表情（登录后含权限信息，前端启动时缓存） |
| `GET /about.json` | 站点统计（话题数/帖子数/用户数） |
| `GET /srv/status.json` | 健康检查 |

### 4.2 认证（见 §3）

### 4.3 分类与话题列表

| 端点 | 用途 |
|------|------|
| `GET /categories.json` | 全部分类 |
| `GET /c/{slug}/{id}.json` | 分类下话题列表（含分类详情） |
| `GET /latest.json`、`/top.json`、`/new.json`、`/unread.json` | 最新 / 热门 / 新帖 / 未读 |
| `GET /tag/{name}.json` | 标签话题列表 |
| `POST /categories.json`、`PUT /categories/{id}.json` | 新建/编辑分类（管理员） |

### 4.4 话题与帖子

| 端点 | 用途 |
|------|------|
| `GET /t/{id}.json` | 话题详情（含前若干帖与 `post_stream`；更多帖子用下一条） |
| `GET /t/{id}/posts.json?post_ids[]=...` | 按 ID 批量取帖子（长话题增量加载） |
| `GET /posts/{id}.json` | 单帖 |
| `POST /posts.json` | **发新话题**：`{title, raw, category_id, tags[], archetype?}`；**回复**：`{topic_id, raw, reply_to_post_number?, nested_post?}`；**私信**：`{archetype: "private_message", title, raw, target_usernames: "a,b"}` |
| `PUT /posts/{id}.json` | 编辑帖子（body：`post[raw]=...`） |
| `DELETE /posts/{id}.json` | 删除帖子 |
| `PUT /t/{id}.json` | 编辑标题（`{title}`） |
| `PUT /t/{id}/status` | 状态：置顶/关闭/归档/可见（`{status, enabled}`，版主） |
| `DELETE /t/{id}.json` | 删除话题 |
| `POST /t/{id}/bookmark` | 书签（新版 bookmarkable 接口，以实测为准） |
| `GET /raw/{id}` | 帖子 Markdown 原文（编辑器"查看源码"用） |
| `POST /post_actions.json` | 点赞 `{post_action_type_id: 2, post_id}` / 举报 `{post_action_type_id: 3, post_id, message?, flag_topic?}` |
| `DELETE /post_actions/{type_id}.json?post_id=...` | 取消点赞/举报 |

### 4.5 搜索

| 端点 | 用途 |
|------|------|
| `GET /search.json?q=关键词&page=N` | 全局搜索；语法支持 `@用户名`、`#分类`、`tag:标签`、`in:title` 等 |

### 4.6 用户与通知

| 端点 | 用途 |
|------|------|
| `GET /u/{username}.json` | 用户资料与统计 |
| `GET /u/{username}/summary.json` | 用户动态汇总 |
| `GET /u/{username}/activity.json?filter=posts|topics|replies|likes` | 用户活动列表 |
| `GET /u/{username}/private-messages.json` | 私信列表（本人） |
| `GET /notifications.json?filter=...&page=N` | 通知列表 |
| `PUT /notifications/mark-read.json` | 全部标记已读 |
| 头像 | `POST /uploads.json`（type=avatar）→ `PUT /u/{username}/preferences/avatar/pick.json`（以实测为准） |

### 4.7 草稿

| 端点 | 用途 |
|------|------|
| `GET /drafts.json` | 草稿列表 |
| `POST /drafts.json` | 保存 `{draft_key, data(JSON字符串), title?, topic_id?, post_id?, category_id?}`；新话题 key 用 `new_topic`，回复用 `topic_{id}` |
| `DELETE /drafts/{draft_key}.json` | 删除草稿 |

### 4.8 上传

| 端点 | 用途 |
|------|------|
| `POST /uploads.json` | multipart：`file` + `type`（`composer`/`avatar`/`profile_background` 等）；返回 `{url, width, height, ...}`；正文中插入 `![alt](url)` |

- 上传有类型/大小白名单（Discourse 默认设置），响应含错误时按 4.10 处理。
- 图片 URL 是站内相对路径（同域，天然防盗链友好）。

### 4.9 管理/审核（管理员，里程碑 M3）

| 端点 | 用途 |
|------|------|
| `GET /review.json` | 审核队列（举报、待审新帖） |
| `PUT /review/{id}.json` | 审核动作（agree/reject/ignore 等，以实测为准） |
| `PUT /admin/users/{id}/silence.json`、`/suspend.json` | 禁言/封禁 |
| `GET /admin/dashboard.json` | 站点报表（精简展示用） |

> 管理类能力优先用 Discourse 自带后台操作；前端仅做"精简看板"等少量展示，不重复实现管理功能。

## 5. 实时消息（MessageBus）

- 通道通过 WebSocket `/message-bus/{channel}/poll`（同域直连，nginx 已支持 Upgrade）。
- 前端使用官方 JS 客户端 `message-bus-js`（Discourse 前端同款）。
- 常用通道（以源码 `grep -rn "MessageBus.publish" app lib plugins` 实测为准）：

| 通道 | 事件 |
|------|------|
| `/latest` | 最新话题变化（首页刷新） |
| `/categories` | 分类变化 |
| `/topic/{topic_id}` | 话题元数据变化（标题、置顶、关闭） |
| `/topic/{topic_id}/posts` | 新回复、帖子编辑 |
| `/notification` | 新通知（右上角角标） |
| `/user/{user_id}` | 当前用户相关（头像、资料变更） |
| `/unread` | 未读计数 |
| `/staff`、`/reviewable_counts` | 管理事件（M3） |

接入要点：

- 登录后 `MessageBus.start()`，注销时 `MessageBus.stop()`。
- 收到 `/topic/{id}/posts` 后增量拉取 `GET /t/{id}/posts.json?post_ids[]=新增ID` 合并渲染（不要整页刷新）。
- 消息体结构以实际推送为准，开发时先订阅打印调试。

## 6. 错误、限流与容错约定

| 场景 | 表现 | 前端处理 |
|------|------|----------|
| 参数/业务校验失败 | HTTP 422，body `{"errors": [...]}` | 逐条展示错误文案（Discourse 已本地化为中文，见 docs/05） |
| 无权限 | 403（部分未登录接口返回 403/404） | 提示登录或"无权限"；**按钮显隐以 API 返回的 `details.can_*` 为准，不要只靠前端判断** |
| 不存在 | 404 | 展示 404 页 |
| 限流（RateLimiter） | 429，body `errors[]` 含等待提示（部分响应带 `extras.wait_seconds`） | 拦截器统一提示"操作过于频繁，请稍后再试"，可读 `Retry-After`（以实测为准） |
| 服务端错误 | 500/502/503 | 统一错误页 + 日志上报 |

额外约定：

- 列表接口响应一般带 `ETag`/`Last-Modified`，前端可用条件请求做缓存（可选优化）。
- 所有写操作失败**不静默**：toast + 控制台日志，便于联调。
- 前端 API 客户端统一封装：注入 CSRF → 序列化表单 → 错误归一化 → 429 重试提示。

## 7. 后端能力扩展（Discourse 插件）

当 Discourse API 或内置行为不满足需求时，在 Discourse 仓库（可写副本，见 docs/06）`plugins/` 下开发插件。常用扩展点（详见 discourse-dev 技能与 `plugin-api-reference.md`）：

| 需求 | 扩展点 |
|------|--------|
| 给话题/帖子/用户加自定义字段并通过 API 输出 | `register_*_custom_field_type` + `register_editable_*_custom_field` + `add_to_serializer` |
| 自定义审核对象类型 | `register_reviewable_type` |
| 自定义报表/统计 | `add_report`、`register_stat` |
| 新增业务端点 | Rails Engine（`config/routes.rb` + `mount`），控制器内复用 Guardian 权限 |
| 扩展 API Key 权限域 | `add_api_key_scope` |
| 内容处理钩子 | `listen_for :event`（DiscourseEvent）、modifier |
| 前端注入（若需在 Discourse 原生后台加东西） | `assets/javascripts/discourse/connectors/<outlet>/`、apiInitializer |

插件开发纪律：改完必须重启服务（`bin/dev` 重启；新增/删除文件后先 `rm -rf tmp`）；每个受限动作都要过 Guardian；写 RSpec + QUnit 测试。

## 8. 异步集成（Webhook，可选）

Discourse 后台可配置 Webhook（事件：`topic_created`、`post_created`、`post_edited`、`user_created`、`reviewable_created` 等），POST JSON 到我们的回调服务。用途：

- 统计/报表数据管道；
- 内容安全外挂服务（接第三方审核）；
- 搜索引擎索引同步（若未来引入外部搜索）。

Webhook 端点必须验证 `X-Discourse-Event-Signature`（HMAC，密钥在后台配置）。

## 9. 数据同步边界与缓存

- 前端不建业务数据库；需要缓存时用内存/本地缓存，并订阅 MessageBus 失效。
- 高频只读数据（分类树、站点配置）登录后拉取 `/site.json` 缓存，订阅 `/categories` 失效更新。
- 帖子内容一律用服务端 `cooked`（已消毒）渲染，**禁止前端自行渲染用户 Markdown**（XSS 防线，见 docs/08）。
