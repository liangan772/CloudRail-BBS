# 09 开发工作流程

> 本文档定义团队如何协作开发：从需求到发布的完整流程。默认单人或小团队（1~5 人），流程保持轻量，随团队扩大再补充。

## 1. 总体原则

- **文档即代码**：docs/ 随功能一起改、一起评审；本套文档是唯一事实来源之一，过时即修。
- **短迭代**：2 周一迭代（里程碑见第 8 节），每迭代结束有可演示产物。
- **小步提交**：功能拆小 PR，评审友好，便于回滚。
- **Discourse 优先复用**：遇到新需求先问「Discourse 现成能力能否覆盖」，再考虑自研或插件。

## 2. 仓库与分支模型

```
E:\CloudRail\
├── docs/          # 本套开发文档（与代码同步维护）
├── web/           # 自研前端（M0 创建）
├── discourse/     # Discourse 源码可写副本（仅插件开发时引入，建议 git submodule 或独立仓库）
└── deploy/        # nginx 配置、docker-compose、部署脚本（M0 创建）
```

分支模型（GitHub Flow 精简版）：

- `main`：始终可部署。直接推送仅限文档/配置微调，代码必须走 PR。
- `feature/<模块>-<简述>`：如 `feature/topic-list`、`fix/upload-422`。
- `release/<版本>`：发版前从 main 切出，只收修复；验证后打 tag 并合并回 main。

提交规范（Conventional Commits，commitlint 强制）：

```
feat: 话题详情支持楼层跳转
fix: 上传图片 422 时错误提示不友好
docs: 补充 Discourse 上传接口说明
refactor|test|chore: ...
```

## 3. 任务流转

- 任务入口：GitHub Issues（模板：`bug` / `feature` / `tech-debt`），标题写清「做什么、为什么、验收标准」。
- 里程碑：`M0~M4`（第 8 节）；迭代内用看板列：`待办 → 进行中 → 评审中 → 已完成`。
- 每次只做一件事：从「待办」认领 → 建分支 → 开发 → 自测 → PR → 合并。

## 4. 开发循环（单人/多人通用）

```
需求/Issue → 设计（改 docs/ 对应章节）→ 实现 → 本地自测 → PR → CI 通过 → 评审 → 合并
→ 部署 staging → 验收 → 合入 main → 发版
```

规则：

1. 涉及架构/API/数据决策的改动，**先改文档再写代码**（文档在 PR 中一并评审）。
2. 实现前跑一遍 `docs/06 §5` 联调清单，确保环境可用。
3. 提交前必跑 `pnpm lint` + `pnpm typecheck` + 相关单测。
4. PR 模板：改动内容 / 测试方式 / 影响面 / 关联文档。

## 5. 代码评审清单

前端：

- [ ] 所有用户可见文案走 i18n（中文默认）
- [ ] 帖子内容只用服务端 `cooked`，无前端 Markdown 渲染
- [ ] 所有写操作带 CSRF token；429/403 有统一处理
- [ ] 权限按钮以 API 返回的 `can_*` 为准，不做前端猜测
- [ ] 列表分页/增量加载正确；无 N+1（前端侧注意批量请求）
- [ ] SSR 无 `window` 直用（放在 `onMounted`/`useAsyncData`）

Discourse 插件（如适用）：

- [ ] 每个受限动作过 Guardian
- [ ] 迁移符合 discourse-migration 规范（已发布不可改）
- [ ] 枚举设置对应 `EnumSiteSetting` 类
- [ ] 序列化器字段用 `add_to_serializer` 且确保被加载

## 6. 发布流程

1. `main` 通过全部 CI；在 staging 完整跑 E2E + 契约测试。
2. 版本号语义化（前端 `web/package.json`；Discourse 用其自身版本，不自定义）。
3. `CHANGELOG.md` 记录用户可见变更。
4. 打 tag（如 `web-v0.1.0`）→ 部署生产（滚动：先 Discourse 无感知，再前端）。
5. 灰度：先开放给内部用户，观察日志与监控 24h 后全量。
6. 回滚预案：前端保留上一版本镜像/构建产物（nginx 一键切回）；Discourse 升级回滚=恢复备份（docs/08 §4）。

发布检查表：备份已做（Discourse）/ 前端镜像已构建 / 监控告警在线 / CHANGELOG 已更新 / 合规项无变化。

## 7. 协作节奏（建议）

| 频率 | 活动 |
|------|------|
| 每日 | 站会（3 句：昨天/今天/阻塞），异步群聊 |
| 每迭代（2 周） | 迭代计划 + 迭代回顾（改流程，回写本文档） |
| 每月 | Discourse 上游版本检查（升级评估，docs/08 §4） |
| 每迭代 | 文档走查：docs/ 是否与代码一致 |

## 8. 里程碑计划

| 里程碑 | 周期 | 内容 | 验收标准 |
|--------|------|------|----------|
| **M0 环境与骨架** | 第 1 周 | Discourse Docker 实例、`web/` 骨架（Nuxt + lint + CI 首条流水线）、nginx 代理雏形、本套文档基线 | 联调清单 6 项全通过；CI 绿灯 |
| **M1 MVP** | 第 2~5 周 | docs/01 §3.1 全部功能 | 用户可完成注册→发帖→回复→搜索→查看通知全流程 |
| **M2 体验增强** | 第 6~8 周 | docs/01 §3.2（实时、点赞、私信、上传、草稿） | E2E 关键路径 6 条全绿；实时通知延迟 < 3s |
| **M3 社区治理** | 第 9~11 周 | docs/01 §3.3（审核、敏感词、封禁、报表）+ 中文搜索优化评估 | 版主可完成举报→审核→处置闭环；敏感词生效 |
| **M4 上线准备** | 第 12~13 周 | SEO、性能压测、监控告警、备份演练、安全加固、备案、灰度发布 | 压测达标；监控告警在线；备案完成；正式发布 |

每里程碑结束：更新本套文档（含 CHANGELOG）、演示产物、遗留问题清单。

## 9. 文档维护规则

- 新增/变更架构决策：改 docs/02；新增功能：改 docs/04；新端点：改 docs/02 §5 表格。
- 文档与代码同 PR 评审；发现过时立即开 `tech-debt` Issue 修正。
- 本文件（docs/09）的流程修订走 PR，记录在 CHANGELOG。
